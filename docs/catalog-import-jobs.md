# Catalog import jobs

The job API provides a durable, chunked backend alongside the existing seller import wizard. It does not replace or change the legacy `/api/vendor/:storeId/imports` workflow.

## Lifecycle

1. `POST /api/vendor/:storeId/imports/jobs` creates an `UPLOADING` job with source metadata, format, mode (`create`, `update`, `mixed`, or `skip`), mapping, and a chunk size from 10 to 50 rows (default 50). Its raw request body is capped at 16 KiB and is fully size-checked before JSON parsing.
2. `POST /api/vendor/:storeId/imports/jobs/:jobId/rows` appends one consecutive, replay-safe block of at most 50 source rows. Each row is limited to 8 KiB, and the raw request is limited to 512 KiB before JSON parsing. An exact replay is accepted; a changed payload for an existing row number returns a conflict. The job accepts at most 100,000 rows. Row numbers are one-based data-row numbers, excluding the file header.
3. `PATCH /api/vendor/:storeId/imports/jobs/:jobId` with `{"action":"finalize"}` moves a non-empty job to `QUEUED`.
4. `POST /api/vendor/:storeId/imports/jobs/:jobId/process` processes at most the configured chunk size in one database transaction. A worker/client may call it again while the job remains `PROCESSING`.
5. `GET /api/vendor/:storeId/imports/jobs/:jobId` returns job counters and a bounded page of row outcomes/errors.
6. The same PATCH endpoint supports `pause`, `resume`, `cancel`, and `retry_failed`. The raw retry request is limited to 1 MiB before JSON parsing. Failed rows can be replaced during retry, including changing the product SKU; replacement SKUs must be unique among the replacement rows and all other staged job rows. Row SKU values and the job's first-row SKU registry are reconciled in the retry transaction.

The job, staged source rows, normalized SKU registry, product writes, row outcomes, and progress counters are persisted. Row staging uses a unique `(jobId, rowNumber)` key and compares a replay's JSON payload with the stored payload; a mismatch is rejected. Processing locks the store and job in the chunk transaction. Product, inventory, adjustment, variant, row-outcome, and counter changes commit or roll back together.

SKU canonicalization is explicit: NFKC, removal of leading/trailing ASCII HT through CR and space (after NFKC), then ASCII-only `A`–`Z` folding. Non-ASCII characters remain case-sensitive (`I` and `i` match; `İ` and `i`, `ı` and `i`, and `Ə` and `ə` do not). This avoids locale-dependent case conversion; NFKC compatibility forms can still map to ASCII before folding. Product SKU uniqueness remains store-scoped, while variant SKU uniqueness remains global; product and variant SKUs are separate namespaces. Vendor manual creation/update, the legacy vendor importer, job importer, and admin product writes use this same JavaScript canonicalizer before lookup and persistence.

The current additive migration `20261106030000_canonical_sku_uniqueness` creates unique expression indexes for those existing scopes. It requires PostgreSQL 13+ and UTF8, aborts if existing rows collide under its canonical expression, and does not rewrite or backfill rows. The SQL uses `translate()` and `"C"` collation, not locale-dependent `lower()`. JavaScript and PostgreSQL both invoke NFKC, but exact output parity is not guaranteed by the source: `String.prototype.normalize` uses the Unicode data bundled with the deployed Node.js/ICU build, while PostgreSQL uses the Unicode data bundled with its server build. The current development runtime reports Node 24.18.0, ICU 78.3, Unicode 17.0; the target PostgreSQL build and its Unicode data have not been verified. Therefore the migration must remain unapplied until an isolated PostgreSQL test compares the supported SKU vector and collision results on the actual target build.

If that parity cannot be established or kept stable across upgrades, use an additive canonical-key design rather than a PostgreSQL NFKC expression: add nullable product and variant canonical-key columns; generate the key in the application with a pinned Unicode implementation/version; write it alongside the display SKU in every manual/import path; and create the existing store-scoped product and global variant unique indexes over those key columns (never a cross-namespace index). Before indexing existing data, run a read-only preflight using that exact pinned implementation, report collisions separately by scope, and require an owner-approved resolution plan before any backfill. This preserves current raw/display SKUs and scopes, but a staged rollout must update every writer before relying on the indexes. Because PostgreSQL cannot independently recompute that pinned application key without adopting the same implementation in the database, direct database writers would need to be prohibited or separately made to follow the same contract. This alternative requires a reviewed migration and backfill plan; it is not implemented here.

The row staging and retry endpoints enforce raw-body byte caps while reading the request stream, before JSON parsing. They reject invalid declared lengths, declared/actual size mismatches, incomplete bodies, oversized requests, invalid UTF-8, and malformed JSON as distinct safe error codes.

The chunk processor uses a PostgreSQL savepoint around product/variant/inventory persistence. If a persistence operation fails, it rolls back that savepoint, marks the entire chunk failed (no rows are reported successful), and commits row outcomes and counters so the seller can correct failed input or retry. This recovery path requires integration testing against PostgreSQL; mocked tests do not prove transaction-abort or savepoint behavior.

All endpoints require an authenticated vendor who owns the route's store, and job queries also constrain by both job ID and that owned store ID. Source row JSON is retained as durable retry input, with per-row size and total-row caps; the original uploaded file itself is not stored. `sourceSizeBytes` and `sourceChecksum` are caller-provided metadata and are not independently verified because the job endpoints accept row blocks rather than file uploads.

## Current boundaries

- The seller UI is not connected to these job endpoints yet. The existing importer remains limited to its current synchronous workflow.
- CSV/XLSX parsing and file streaming are not part of this backend foundation. A client/adapter must parse a source and send bounded row blocks.
- Processing is request-driven, not a continuously running worker. A durable worker scheduler, lease/heartbeat, and automatic recovery from process termination remain future work; the row/job transaction lock prevents concurrent chunk commits but a crashed request may need an explicit resume.
- `ImportJobSku` detects duplicate source SKUs across staged blocks. Catalog matching and all product reads are store-scoped.
- Chunk limits are conservative defaults, not benchmark-derived throughput claims. Database-backed integration tests, migration application, and 10k+ scale benchmarks are still required.
- Retention settings are exposed as `CATALOG_IMPORT_COMPLETED_RETENTION_DAYS` (default 90), `CATALOG_IMPORT_FAILED_RETENTION_DAYS` (default 180), and `CATALOG_IMPORT_CANCELLED_RETENTION_DAYS` (default 30), each bounded to 1–3650 days. They document the intended retention window only; there is no automatic deletion or archival job. Any cleanup must be separately reviewed and owner-approved.
- For a rough storage planning case, 100,000 rows averaging 1 KiB of staged JSON represent about 100 MiB of payload before PostgreSQL row/TOAST overhead and indexes. A planning allowance of 150–200 MiB per such job is reasonable but unmeasured; actual catalog row shape and index/TOAST behavior must be benchmarked. Retention and quotas should be set before broad rollout.

Migration `20261106020000_catalog_import_jobs` is additive and has not been applied.
