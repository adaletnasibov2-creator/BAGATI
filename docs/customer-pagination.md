# Customer pagination

## Order history API

`GET /api/orders` remains customer-session protected and keeps the existing top-level `items` response field. It now returns at most 20 rows by default (maximum 50) and adds a `pagination` object with `pageSize`, `hasNext`, `hasPrevious`, `nextCursor`, and `previousCursor`. Pass the opaque cursor returned by the API as `?cursor=...`; optionally pass `pageSize` from 1 to 50. The query remains scoped to the authenticated user's ID. List rows contain only the order summary, store names/item counts, and payment statuses needed by the customer history list; the detail page remains separate.

This is an intentional row-shape reduction: the old list response included full order scalars, each store-order's full `items` collection, and payment amount/currency/timestamps. No in-repository frontend calls this GET endpoint; the existing customer history page is server-rendered. The authenticated `/orders/[orderId]` page loads its own full detail, but the project has no separate order-detail API route. External clients that depended on the old list fields must update to the summary contract; any external full-detail API need should be designed as a separate authorized endpoint. Authentication and ownership scope are unchanged.

The customer order-history page performs the same user-scoped, bounded query directly as a server component. Its previous unbounded load is removed. Cursors encode the sort boundary, not an identity or authorization grant. The server always combines the boundary with the authenticated user's ID.

## Product and store discovery

`/products` and `/stores` accept an opaque `cursor` query parameter for forward/back navigation. Their links preserve the current filters and sort; submitting changed filters starts from the first page. Product pages return up to 48 products; store pages return up to 24 stores. Product and store cursor requests scan at most 500 candidate rows plus one probe row per request, and fetch the selected page separately (at most 50 records). Sparse eligibility can therefore require several requests. When a scan window contains no eligible result but more candidates remain, the response supplies a same-direction progressing cursor and the page shows a “continue searching” action. It does not silently skip the unscanned portion. If a cursor page has no eligible results and no more candidates in that direction, an empty page can offer one reverse recovery cursor; recovery cursors cannot create an endless empty-page loop.

The product page's store selector uses `GET /api/store-options`, which returns no more than 20 eligible options per request and supports bounded text search, city filtering, and cursors. A full-data bounded alternative is available at `GET /api/stores/cursor`; it retains the legacy store fields within `items` and adds cursor metadata. The existing `GET /api/stores` response is unchanged because the repository cannot establish whether external consumers rely on its `{ items }` shape; it remains an unpaginated legacy endpoint. External consumers cannot be verified from source alone.

The existing `GET /api/products` endpoint is also retained unchanged: it returns its legacy `{ items, page, limit, total }` response and still uses offset pagination/counting. No in-repository caller was found. The new bounded alternative is `GET /api/products/cursor`, which retains the product item fields and returns `{ items, pageSize, hasNext, hasPrevious, nextCursor, previousCursor }` without a full-result count. External clients are unknown, so migration to the cursor endpoint must be coordinated before deprecating the legacy route.

Example first-page requests:

```text
GET /api/products/cursor?city=baku&sort=newest&q=linen
GET /api/stores/cursor?city=baku&q=local
```

Both cursor API responses contain `items`, `pageSize`, `hasNext`, `hasPrevious`, `nextCursor`, and `previousCursor`. To continue, repeat the same route and filters with `cursor=<URL-encoded nextCursor>` or `cursor=<URL-encoded previousCursor>`. Omit `cursor` to restart at the first page. The product cursor API uses a fixed page size of 20; the store cursor API uses 20. Product cursors are tied to the selected sort mode; a mismatched sort/cursor is treated as invalid and restarts the product page with a warning. Invalid or overlong cursors return HTTP 400 from the APIs. Neither cursor endpoint returns an exact total.

Server-rendered product and store search terms are trimmed and limited to 120 characters; oversized terms display a validation message and are not sent to the search predicate. `/api/products/cursor`, `/api/stores/cursor`, and the server-rendered discovery pages use the same 120-character maximum. The store-option API remains separately limited to 80 characters because its search control has that input limit.

No exact totals are presented for product or store cursor pages. This avoids a full-catalog count/scan solely to render pagination controls. Pagination is keyset-based; concurrent inserts, deletes, renames, eligibility changes, or product name edits can alter page membership between requests. Tuple ordering is deterministic for a stable dataset, but these cursors are not a cross-request snapshot. The legacy product API can still perform a count and deep offset query by design until its consumers migrate.

The automated cursor tests use query-aware in-memory mocks. `npm.cmd run test:customer-order-pagination`, `npm.cmd run test:public-product-catalog`, `npm.cmd run test:public-store-discovery`, and `npm.cmd run test:search-term` verify tuple boundaries, sparse scanning in both directions, page completeness for fixed data, input bounds, and response construction. They do not establish PostgreSQL collation, Prisma cursor behavior, transaction behavior, or query-plan performance.

`npm.cmd run test:pagination:postgres` provisions a new PostgreSQL cluster in a unique `%TEMP%` directory using already-installed PostgreSQL binaries, binds the temporary server to `127.0.0.1` on an ephemeral non-default port, creates a role limited to the fresh `bagati_pagination_test` database, runs the identity/privilege preflight, applies the existing migrations only to that fresh database, runs the focused unit and database integration tests, then stops and removes only the run directory carrying its unique ownership marker. The runner does not read or overwrite `.env`/`.env.local`. Prisma CLI automatically loads project `.env`, so the runner supplies a process-scoped `DATABASE_URL` that takes precedence and targets only the temporary database; the identity/privilege preflight must pass before Prisma migration deploy runs. The integration test requires `BAGATI_PAGINATION_TEST_DATABASE_URL` explicitly and never falls back to `DATABASE_URL`. It refuses to continue if the local PostgreSQL binaries are unavailable, the test role is privileged, the ordinary `bagati` database exists on the test cluster, or the role can connect to any other database. It does not install packages or alter the Windows PostgreSQL service.

Prerequisites are PostgreSQL server binaries (`initdb.exe`, `pg_ctl.exe`, and `psql.exe`) already installed. If they are not on `PATH` or under `C:\Program Files\PostgreSQL\18\bin`, set the process environment variable `BAGATI_PG_BIN` to the existing PostgreSQL `bin` directory before running the command. No password or URL needs to be copied into a file or chat; the runner generates disposable credentials in process memory and a private temporary directory. The isolated integration test first performs a read-only preflight of current database, current role, loopback server address/port/version, database ownership, role capabilities, and ability to connect to the ordinary `bagati` database. Fixture writes occur only after that preflight passes.

The focused unit commands can also be run independently: `npm.cmd run test:customer-order-pagination`, `npm.cmd run test:public-product-catalog`, `npm.cmd run test:public-store-discovery`, and `npm.cmd run test:search-term`. The database integration suite is `npm.cmd run test:pagination:integration`, but it intentionally fails closed unless the dedicated URL points to the expected local loopback test role/database and the connected server passes the preflight. Do not manually point it at the application database. On affected Node 24 Windows environments, the runner applies a temporary child-process-only `os.userInfo()` fallback to work around `uv_os_get_passwd returned ENOMEM`; it is created under the owned temp directory and removed during cleanup, and does not alter application code or global environment settings. The isolated runner does not create persistent databases; it removes its own fresh cluster only after a successful stop and ownership-marker check. If stopping fails, it leaves the owned temporary directory intact and reports its path for manual recovery.

PostgreSQL tests exercise Prisma's actual ordering and query predicates on this temporary cluster; they do not establish production query plans, production collation, or consistency across page requests while production data changes. The ordinary local `bagati` database, production, and the Windows PostgreSQL service are not used or modified by this runner.
